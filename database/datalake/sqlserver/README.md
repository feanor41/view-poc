# Native SQL Server reporting synchronization

The standalone `src/Datalake/Vwp.Datalake.SqlServer` console uses Change Tracking and server-side SQL. The default synthetic sources are `VwpEtlAccounts` and `VwpEtlFinancials`; the separate reporting database is `Datalake`. These defaults do not change the original view PoC databases.

Run `bootstrap`, `sync`, or `observe` through the console. `bootstrap` explicitly creates missing synthetic source tables, enables source Change Tracking and snapshot isolation, creates source epoch metadata, and prepares the reporting schema. Run it only with an authorized bootstrap identity. The ordinary `sync` worker performs no source DDL. Runtime source access requires `SELECT` on the eight captured tables and source identity table, and `VIEW CHANGE TRACKING` on each captured table. Target access must permit writes to the mirror, projection and `etl` tables and acquisition of the application lock.

| Environment setting | Default | Meaning |
| --- | --- | --- |
| `VWP_SQLSERVER_CONNECTION` | Required | SQL client connection string supplied through the environment; never printed |
| `VWP_SQLSERVER_ACCOUNTS_DATABASE` | `VwpEtlAccounts` | Accounts source database |
| `VWP_SQLSERVER_FINANCIALS_DATABASE` | `VwpEtlFinancials` | Financials source database |
| `VWP_SQLSERVER_DATALAKE_DATABASE` | `Datalake` | Reporting database on the same instance |
| `VWP_ETL_MAX_ROWS` | 1000 | Maximum raw rows and, separately, projection rows applied per invocation |
| `VWP_ETL_MAX_BYTES` | 1048576 | Serialized UTF-16 payload budget per raw batch; conservative projection size estimate budget |
| `VWP_ETL_MAX_WINDOW_ROWS` | 1000000 | Complete captured window and pending projection fanout safety ceiling |
| `VWP_ETL_MAX_WINDOW_BYTES` | 268435456 | Complete serialized staging window safety ceiling |
| `VWP_ETL_POLL_SECONDS` | 30 | Pause between completed windows in loop mode |
| `VWP_ETL_RETENTION_YEARS` | 5 | Reporting retention policy metadata, minimum five; no automatic purge |
| `VWP_ETL_CT_RETENTION_DAYS` | 7 | Source capture metadata retention configured during bootstrap |
| `VWP_ETL_COMMAND_TIMEOUT_SECONDS` | 120 | SQL command timeout |

Window row/byte budgets and batch byte budgets accept positive 64-bit integers; per-application row limits and timing settings accept positive 32-bit integers. Database identifiers are validated and safely quoted. Datalake records its source database names and refuses a different source configuration. Changing the sources requires a distinct target database.

`sync` captures a window if none is pending and applies one bounded continuation batch. Invoke it repeatedly until `observe` reports `pendingWindows: 0`. `sync --loop` drains pending continuation batches immediately, then waits for the configured polling interval before capturing another window. One session-owned `sp_getapplock` prevents concurrent writers for the same target. `sync --resnapshot` explicitly discards pending work and current mirrored state, then starts a fresh source snapshot. It must be an intentional recovery operation, not an automatic retry.

The source tables are the original PoC shapes: Accounts, Assets, ContactInformation and AccountHistory from the Accounts source; PaymentMeans, Operations, Transactions and CollectionOrders from Financials. Existing AccountHistory rows are mirrored; the worker does not generate new business history. Physical `dbo.AccountOperations` joins current Operations to current Accounts with a left join. Missing or deleted Accounts leave the Financials-owned Operation present with nullable AccountName, AccountStatus and SourceAccountCreatedAt, and `AccountMissing=1`. Operation deletion removes the projection. Reparenting and Account changes propagate through a durable projection queue.

Synthetic bootstrap reproduces source column shapes and primary keys, rather than the original service identities, grants and foreign keys. This allows deliberate inconsistent-relation fixtures. Bootstrap preserves constraints on already-existing source tables. The original view PoC initializer and databases are separate from the synthetic demonstration.

The source, mirrored target and AccountOperations reporting schema contracts are fixed for this PoC. Before capture and application, the worker verifies complete column shapes, SQL types, lengths, precision/scale, nullability, generated-column status and the single-column Id primary key. Schema drift fails before publishing or advancing progress, including numeric precision changes that could otherwise silently round staged values. Restore the expected source/target definitions before explicit resnapshot; this worker does not automatically migrate contracts.

Capture uses one snapshot transaction across all three databases. Initial data, both source versions, incremental changes and current source values belong to that transaction boundary. The full window is staged durably before bounded application begins. This prevents a truncated change query from advancing a checkpoint past skipped changes. It also means extraction enumeration, initial snapshot staging and row version retention can be expensive: the row and byte budgets bound retained staging and reject oversized windows, but do not establish a production source-work or transaction-duration bound. Raising safety budgets requires deliberate resource evaluation. Source snapshot staging can be repeated after a capture rollback; an already committed window is resumed without re-reading it.

Each application transaction updates raw mirrors, queues affected Operations, applies a bounded projection subset and removes consumed staging rows. Raw and derived work can be partially caught up while a window remains pending; the fully completed window is the checkpoint boundary. Only after both staging and projection queues drain does a transaction advance both checkpoints and delete the window. Crashes around that transaction either preserve the previous checkpoint or preserve the new one. Target reporting readers must choose an isolation level appropriate for consistent multi-query reports; the PoC does not publish an entire large window in one transaction.

Before a new incremental window, all table minimum valid versions, table capture identities (`object_id` and `begin_version`) and both source epochs are checked. Capture retention expiry, tracked table reset or a backwards version causes failure and requires explicit resnapshot. Per-table identities are captured in `etl.WindowTables` and committed to `etl.TableCheckpoints` only when the window drains. This detects `TRUNCATE` even when its minimum valid version equals the last checkpoint. After a source restore with data loss, administrators must update `dbo.VwpEtlSourceIdentity.Epoch` to a new GUID before resuming the worker: Change Tracking version comparison alone cannot reliably detect restored timelines. Source identity metadata does not automatically detect every restore. Pending durable windows can finish without source capture history; the next capture validates the current source timeline.

`observe` emits JSON metadata estimates for business table row counts (`countsEstimated: true`), exact staging/queue counts within configured window budgets, staging bytes, window age, retention metadata and elapsed capture-to-completion duration (`lastWindowApplyMs`, including capture work and any waits). Business counts use `sys.partitions` to avoid repeatedly scanning growing historical tables during each continuation batch; independent verification uses exact comparisons. These are pipeline measurements. Change Tracking has no originating business event timestamp; use the synthetic verifier's externally measured source commit-to-report duration for end-to-end freshness. No local result establishes capacity for two million vehicles or five million daily transactions.

Failure hooks use `VWP_ETL_FAULT`: `after-stage-commit`, `before-apply-commit`, `after-apply-commit`, `before-checkpoint-commit`, and `after-checkpoint-commit`. They fail the command without printing SQL payloads or credentials. Unset the hook and resume `sync`. `VWP_ETL_HOLD_LOCK_SECONDS` and `VWP_ETL_HOLD_SNAPSHOT_SECONDS` accept 0–300 seconds for deterministic concurrency tests and emit a safe JSON event before waiting. No hooks are active by default.

Retention is independent from capture retention. No age-based history deletion, purge job or multi-year transaction dataset is created. Transactions in the original PoC have no business event date, so this implementation does not invent one for partitioning. Production partition design requires actual transaction dates, retention semantics, reporting filters, row fanout and measured index/maintenance costs. The current target indexes support Operation-to-Account fanout, Transaction-to-Operation lookups and AccountHistory date lookups; they are a PoC baseline, not a nine-billion-row storage claim.
